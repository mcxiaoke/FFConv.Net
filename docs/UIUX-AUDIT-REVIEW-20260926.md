## 一、结论速览

| 方案 | 审计建议 | 评审结论 | 理由（一句话） |
|---|---|---|---|
| **C** 实时回显 | P0 | **做，但要砍掉一半范围** | 解析结果可即时回显；"实时生成命令"做不到（要 ffprobe + 硬件探测） |

## 二、逐方案核对

### 2.1 方案 C（实时回显）——方向最对，但范围要砍

**站得住的部分**：`GuiOptions.ParsedArgs` 确实是惰性缓存的 `CliArgsParseResult`，`Accepted / Warnings / Values` 三个字段已齐备（`CliArgParser.cs:13-23`），不需要新增映射逻辑。审计说"只需投影成可读文本"属实。

**站不住的部分**：审计给的回显样例里最后两行是

```
生成命令（预览）：
ffmpeg -i in.mp4 ... -c:v hevc_nvenc ... out.mp4
```

这条**不可能随输入实时刷新**。原因在 `GUI-DESIGN-20260925.md §7.1`：预览不是拼字符串，而是真跑 `RunFFmpeg(entry, TestMode=true)`，要先完成真实的 `ResolveHwPlan`（硬件探测，首次 2–3 秒）与 `CreateFfmpegArgs`（ffprobe 探测）。`HwDetect` 的探测子进程**不接收取消信号**（`§7.5` 已记录）。因此：

- 在 `TextChanged` 里刷新命令 = 每敲一个字符触发一次 2–3 秒的同步阻塞；
- 放在后台线程 = 用户改 5 次就并发 5 个探测进程，且无法取消。

**修正后的方案 C**：回显**只做解析层**，命令仍由「预览命令」按钮产出。回显内容为：

```
✓ 4 项生效  ·  覆盖控件：Preset 下拉  ·  ! 1 项告警（点击展开）
```

明细里给：哪些参数被接受、哪些被忽略及原因、哪些覆盖了界面控件（`CollectOverrideNotes()` 已有，`GuiOptions.cs:195`）、码率是否会被换算/丢弃。这些全是纯字符串计算，无 IO。

### 2.2 方案 A + B（参数面板 / 表单化）——收益真实，成本被低估

收益没问题：29 项生效参数里确实只有 9 项有控件，其余 20 项要盲写 CLI 写法。

**但审计没有算两笔账**：

**(1) 双真值源问题。** 现在 `GuiOptions` 的契约是单向的：**CLI 参数框 > 界面控件**（`GuiOptions.cs:16-18`，`EffectivePreset` / `EffectiveHwaccelValue` / `Flag()` 全是"取不到 CLI 值才回落控件"）。一旦给 `--video-quality` 之类加了常驻 `NumericUpDown`，就必须回答：

- 用户改了控件，参数框里已经手写了 `--video-quality 23`，谁赢？
- 参数框里删掉 `--video-quality` 后，控件值是"用户填的"还是"未设置"？
- `ShadowedBy` 那 9 项（preset / output / hwaccel / …）要保留"控件 > CLI"还是反过来？

这是个双向同步状态机，每个参数都要定规则。`tests/MediaCli.Transcode.Tests/GuiMappingTests.cs` 现在断言的是"同一组输入 → 与 CLI 逐字节一致"，控件化后这批断言要么重写、要么失效——这是当前 300 项测试契约里最值钱的部分。

**(2) 布局空间已吃满。** 实测坐标（`MainForm.cs`）：

| 区块 | y 区间 | 高 |
|---|---|---|
| 输入 | 12–122 | 110 |
| 输出 | 130–222 | 92 |
| **参数** | **230–388** | **158** |
| 操作 | 396–460 | 64 |
| 日志 | 468–756 | 288 |

`ClientSize` 1000×800（`:100`），`MinimumSize` 880×640（`:101`）。日志组 756 结束后底部仅剩约 44px 余量。也就是说：**参数区想增高，只能从日志区身上割**。日志框当前 214px，若压到 176px（已偏窄），参数区也只多 38px → 196px。而方案 A 的草图有 5 个折叠组：5 个组头 ≈ 140px + 顶部两行 ≈ 60px = 200px，**全折叠都放不下**，展开任一组再 +90px。

所以方案 A 若要落地，形态应该是**主窗口加一个「参数」页签（TabControl）**，把折叠组放进独立页面，而不是在 158px 的 GroupBox 里堆叠。同时「日志区可折叠」（审计列为 P2）会变成 A 的**前置依赖**，不是可选项。

### 2.3 方案 D（联动约束）——前提有误

审计写："`decodeMode=gpu` 时 hwaccel 不能为 `cpu`"。

核对 `HwDetect.cs`：`HwaccelNames = ["cuda","qsv","amf","d3d","cpu"]`（`:64`），`NormalizeHwaccelName("cpu")` → `"cpu"`（`:293`）。gpu 分支只要求 `caps.Usable[name]` 为真（`:310`），cpu 层恒可用 → **不抛错**，候选链返回 `["cpu"]`。

即 `decodeMode=gpu + hwaccel=cpu` 在 core 里是**合法**的，语义上等价于软解，不是无效组合。按审计去做下拉过滤会**误伤**（且 `decodeMode=cpu` 才是"强制软解"的正规入口，`GUI-DESIGN §6.1` 有说明）。

**同一处还发现一个更值得修的点**：`hwaccelCombo` 列了 9 项（`MainForm.cs:275`），但 `HwaccelAliases`（`HwDetect.cs:60-63`）把 `d3d11va / d3d12va / dxva2` 全部归一为 `d3d`。也就是说下拉里 **d3d / d3d11va / d3d12va / dxva2 四项完全等价**——用户选哪个结果都一样。这比"联动过滤"更影响理解，建议下拉收敛为 `auto / cuda / qsv / amf / d3d / cpu`，并在 tooltip 里说明 d3d 涵盖 d3d11va/d3d12va/dxva2。

D 里**可以保留**的是文案部分：输出模式 `dir/tree/file` 改中文、复选框加 tooltip——零风险，直接做。

### 2.4 方案 E（使用说明增强）——应该提前

38 项参数（`CliOptions.All` 实测 38 项，不是审计写的 40 项）现在是一个 4 列 ListView（`AboutForm.cs:250-284`），只能滚。加一个关键字过滤框（按 `Name` / `Aliases` / `Description` 匹配，`Description` 字段已存在）+ 双击复制 `--name value`，成本约 30 行，且与新方案 G 直接配套（G 负责"填"，E 负责"查"）。

### 2.5 方案 F（输入辅助）——只挑便宜的

- 「重置为默认参数」：成本最低、收益实在，直接做；
- 「最近使用记录」：中等，可做；
- **Tab 补全**：WinForms `TextBox` 没有内置补全（`TextBox.AutoCompleteSource` 只支持文件系统/URL 等固定源，不支持自定义候选）。要实现得自绘候选列表 + 处理键盘消息，是这堆方案里性价比最低的一项，建议排到最后或不做。

## 四、新方案 G：参数构建器（单向）+ 即时回显条

### 4.1 核心取舍

**不新增任何进入 `GuiOptions` 的控件。** 参数框 `cliArgsBox` 保持唯一真值，新控件只负责**生成 `--key value` 文本并写回参数框**。

```
参数构建器（对话框 / 下拉面板）
   └─ 生成 "--video-quality 23" ──写回──> cliArgsBox ──> GuiOptions.ParsedArgs ──> core
                                              ↑ 唯一真值
```

这样：

- `GuiOptions` 语义一行不改，CLI↔GUI 逐字节一致性契约不动，`GuiMappingTests` 全绿保留；
- 不存在"控件 vs 文本谁优先"的双向同步问题——文本就是真值，和 CLI 一致，用户能直接看懂自己到底传了什么；
- 纯 C# 部分只有一个格式化器类，可单测，不引入 WinForms 依赖。

### 4.2 三个组件

**(G-1) 即时回显条**（替代现有静态 `cliArgsHint`）

- 位置：`cliArgsBox` 下方（现 `(80,92)` 那行 hint 的位置，`MainForm.cs:295-302`）；
- 触发：`TextChanged` 防抖 300ms（复用现有 `scanTimer` 那种防抖写法）；
- 内容：`✓ N 项生效 · 覆盖控件 X · ! M 项告警`，点击展开明细；
- 实现：新增纯 C# `ParamStatusFormatter`（无 WinForms 类型），输入 `CliArgsParseResult` + `GuiOptions`，输出一行状态 + 明细文本，可直接单测。

**(G-2) 参数构建器**（解决"必须记住 CLI 写法"）

- 入口：参数框右侧「添加参数…」按钮（参数框宽 882 → 缩到约 780，右侧留位置；或放 `btnAbout` 旁）；
- 形态：对话框，内容全部由 `CliOptions.All` 生成——参数名下拉（带中文 `Description`）+ 按 `Kind` 切换取值控件：
  - `Number` → `NumericUpDown`（speed 附范围 0.5–2.0）
  - `Bitrate` → 数字 + 单位下拉（k/M/G），插入时转裸 bps
  - `Choice` → 下拉（output-mode / decode-mode）
  - `Flag` → 勾选
  - `Text` → 文本框（metadata 附 `k=v;k2=v2` 示例）
- 产出：点「插入」把 `--name value` 插到参数框光标处；已存在的同名参数做替换而非追加。
- 分两步落地也行：**先做轻量版 G-2'**（参数框右键菜单 / 「插入参数▼」分类菜单：编码 / 画面 / 命名 / 筛选 / 元数据，点击插入 `--video-codec ` 并把光标停在值位），半天工作量，已经能解决"记不住写法"。

**(G-3) 说明窗口检索**（= 方案 E 前两项，与 G 配套）

### 4.3 与方案 A/B 的成本对比

| 项 | A+B（常驻控件） | G（单向构建器） |
|---|---|---|
| 新增控件 | ~25 个常驻 | 1 个按钮 + 1 个对话框 |
| `GuiOptions` 改动 | 需重定优先级规则 | **零** |
| 既有测试影响 | `GuiMappingTests` 需重写 | 只新增 `ParamStatusFormatter` 单测 |
| 布局影响 | 参数区 +150px，需加高窗口 / 日志折叠前置 | 参数区高度不变 |
| CLI↔GUI 命令一致性风险 | 中高（双源） | 无（单源） |
| 解决"记不住写法" | 是 | 是 |
| 解决"参数总览" | 是（常驻可见） | 部分（靠说明窗口检索） |

G 的短板只有一条：用户不能一眼扫到"全部参数当前值"。但这恰好是"参数框文本"本身能提供的（它就是 CLI 原样），配合 E 的检索即可覆盖。

## 六、需要你拍板的两点

1. **要不要走 G 主线**（单源构建器），还是坚持 A+B（常驻控件）？如果目标是"让 UI 看起来像专业转码工具、参数一眼全见"，A 的体验上限更高，但要接受 `GuiOptions` 语义调整与窗口加高；如果目标是"最小改动、不碰一致性契约"，G 更稳。
2. **`--max-bitrate` 要不要真的打通？** 现在 core 的 `PresetUserArgs.MaxBitrate` 存在，`ArgvShim` 没有对应字段（`FFmpegPresets.cs:145-163`），所以 GUI/CLI 都传不进去。是改文档（删掉示例）还是补 core+CLI+GUI 三处打通——后者是跨层改动，属范围决策。
